## 3. 底盘帧表（v0.2 定稿）

### 3.1 Jetson → F407

**`0x000` 广播急停（DLC=0，最高优先级）**

CAN 仲裁是 ID 越小优先级越高，`0x000` 能**插队打断一切流量**（包括会抢 ID 排队的 0x020）。
收到后：`chassis_driver_enable(0)`（STBY 拉低）+ 清速度 + 锁存急停。**这是唯一的"硬急停"通道。**

> **v0.2 约定（2026-10-19 双方定）：Jetson 发、F407 只收不发。**
> F407 暂不广播的原因：当前没有故障检测框架（只有 IMU_ONLINE 和看门狗两个状态位），
> 看门狗超时/bus-off/IMU 离线都**不适合**广播急停（见 §3.5 分析）。
> 等"故障检测"专题版本落地后再启用 F407 广播，届时新增 **`cmd = 0x05` = 清故障锁存**
> （不能用 0x04——那是清零里程计，语义不同）。

**`0x020` 速度命令（100 Hz）**

| 字节 | 0 | 1 | 2..3 | 4..5 | 6..7 |
|---|---|---|---|---|---|
| 含义 | `cmd` | `seq` | `vx`（i16 LE，mm/s，+前进） | `vy`（i16 LE，mm/s，+左移） | `wz`（i16 LE，0.01 rad/s，+逆时针） |

`cmd`：`0x01` 速度 / `0x02` 应用级急停（与 `0x000` 不冲突，保留）/ `0x03` 小陀螺 / `0x04` 清零。  
`seq` 8 bit：100 Hz 下 2.5 s 回绕一次，够用。

**`0x021` 标志帧（10 Hz 保活 + flags 变化时立即发）**

| 字节 | 0 | 1..7 |
|---|---|---|
| 含义 | `flags`（bit0 = EN 允许驱动） | 保留填 0 |

> 从 100 Hz 降到 10 Hz：flags 是慢变量，100 Hz 纯浪费带宽；变化时立即发保证响应性。

### 3.2 F407 → Jetson 反馈（100 Hz，`0x110` ~ `0x114`）

把串口 40 B 反馈帧**按 8 字节顺序切成 5 帧**：

| CAN ID | 数据段 = 串口帧字节 |
|---|---|
| `0x110` | 0..7  （`5A A5 81` + `seq回显` + `x[0..3]`） |
| `0x111` | 8..15 （`x[4..7]` + `y[0..3]`） |
| `0x112` | 16..23（`y[4..7]` + `yaw_cdeg` + `vx` + `vy`） |
| `0x113` | 24..31（`wz` + `gyro_yaw` + `gyro_wz` + `status` + `cmd_cnt` + `fb_seq[0]`） |
| `0x114` | 32..39（`fb_seq[1]` + 四轮 RPM×4 + `crc8` + `0x0D`） |

**接收端必须实现组完整性规则**（否则会出现"偶发底盘状态跳变"这种极难查的问题）：

1. 收到 `0x110` → **开新组**，清缓冲；
2. 收到 `0x111~0x114` → 按序填入；
3. 收到下一个 `0x110` 时上组**未拼满** → 丢弃上组；
4. 距 `0x110` 超过 **5 ms** 仍未拼满 → 丢弃（v0.2 定稿：F407 用 TX 队列**连续发**，组内延迟 ≤2 ms，5 ms 有 2.5 倍余量；若 F407 实测组内延迟 >2 ms 会主动通知并上调超时值）；
5. `crc8` 校验失败 → 丢弃整组，**不输出**。

### 3.3 带宽（v0.2 更新）

| 流量 | 帧数/s | 1 Mbps 负载 |
|---|---|---|
| `0x020` @100 Hz | 100 | ≈1.5% |
| `0x021` @10 Hz | 10 | ≈0.15% |
| `0x110~0x114` @100 Hz | 500 | ≈7% |
| 云台 ZDT 命令+遥测 | ~100 | ≈1.5% |
| **合计** | ~710 | **≈10%** |

### 3.4 已确认的三条技术风险（双方知悉）

1. **5 帧反馈不是原子的**：ZDT 扩展帧可能插在中间、某帧可能丢失/被错误帧打断 → 必须按 §3.2 组规则处理（crc8 兜不住组边界问题）。
2. **F407 只有 3 个发送邮箱**：100 Hz × 5 帧 = 每 10 ms 突发 5 帧，`HAL_CAN_AddTxMessage()` 邮箱满会直接失败（实测 `HAL_CAN_ERROR_PARAM`）。
   **v0.2 定案：用 TX 环形队列连续发（组内 ≤2 ms），不用 2 ms 错开**——错开会让反馈整体滞后 8 ms，浪费一帧实时性，不值得；带宽余量充足（500 帧/s 对 1 Mbps 仅约 7%）。
   F407 承诺：实测若组内延迟 > 2 ms 主动告知并同步上调超时值。
3. **`0x021` flags 100 Hz 太浪费**：降到 10 Hz + 变化即发（见 §3.1）。

### 3.5 为什么 F407 暂不广播 `0x000`（边界分析，v0.2 定）

F407 当前没有故障检测框架（只有 IMU_ONLINE 和看门狗两个状态位），三类已有异常都不适合广播急停：

| 异常 | 广播 0x000 有用吗 | 说明 |
|---|---|---|
| 看门狗超时（100ms 收不到命令） | ❌ | 已经停车了；若是 Jetson 掉线，广播也没人收 |
| bus-off（总线故障） | ❌ | 根本发不出去（最讽刺的一点） |
| IMU 离线 | ❌ | 底盘靠编码器仍能跑，IMU 是辅助，不该急停 |

真正该广播的场景（编码器全失效、欠压、驱动芯片故障）需要先做故障检测，属于后续迭代；
届时新增 `cmd = 0x05` = 清故障锁存（不能用 0x04，那是清零里程计）。

## 5. 云台 ZDT 走 CAN（归属 Jetson 侧）

- 扩展帧：`ID = (addr<<8) | packet`；`data = 功能码 + 参数… + 0x6B`。
- 单条命令 >8 字节时按 `packet = 0,1,2…` 拆包，**帧间 ≥2 ms**。
- 地址：yaw=2、pitch=1；**波特率 1 Mbps**。
- 遥测轮询 100~250 ms/项（与串口版一致）。
- **前置（2026-10-21 定）**：ZDT 驱动板通过**面板按键/上位机软件**切 CAN 模式 + 1 Mbps；切换后 CH340 UART 不再使用。
- Jetson 侧实现：`can_transport.cpp` 已有扩展帧拆包骨架，待接 `ZdtCanLink`（复用 UART 版 ZDT 编解码层，只换传输）。
- 注意：标准帧（底盘 `0x020`/`0x021`/`0x110~0x114`）与扩展帧（ZDT）可在同一总线上共存，互不干扰。

## 6. 错误处理

1. **bus-off**：F407 用 bxCAN 硬件级 **AutoBusOff（ABOM）**，检测到连续隐性位后自动恢复，无需软件干预；双方都开自动恢复、不设永久锁死。
2. **告警可见性**：F407 在 `status` 加 `CAN_ERR` 位（§4）；`0x110~0x114` 在 bus-off 期间自然断流 → Jetson 按**反馈超时 100 ms**处理（与串口版看门狗语义一致）。
3. **诊断**：Jetson `candump -td can0`（带时间戳）/ `candump -l can0`（存盘）；F407 `can_test` 的 TEC/REC/LEC 打印（USART1，**CANTEST_SERIAL_DEBUG 必须设 0**——USART1 已被 chassis_debug 占用）。
4. **急停方向**：`0x000` 由 **Jetson 发、F407 只收**；F407 自身异常（看门狗/bus-off/IMU 离线）**不广播**——已有各自的处理方式（看门狗停车、ABOM 自动恢复、外环退回纯运动学），见 §3.5。

### 8.1 `can_link` 正式模块：实现与用法（F407 侧，已完成 2026-10-21）

> 本节只讲**实现方式与使用方式**；实测数据见 §9.1 / §9.2。

#### 文件清单

| 文件 | 作用 |
|---|---|
| `UserLib/Comm/can_link_config.h` | 帧 ID、位时序、队列深度、错误阈值、`CAN_LINK_ENABLE` 开关 |
| `UserLib/Comm/can_link.h` | 对外只有三个入口：`can_link_init()` / `can_link_poll()` / `can_link_state()` |
| `UserLib/Comm/can_link.c` | 实现：CAN 帧 ↔ 12B/40B 协议帧的搬运、TX 队列、错误监测 |

#### 核心设计：协议零重写

`can_link` **不重新实现协议**，只做「搬运」——协议字段、CRC、校验、看门狗全部复用串口版：

```
0x020 (8B) ──► 拼出 12B 命令帧（flags 取自 0x021）──► ulink_apply_cmd12()
40B 反馈   ──► 按 8 字节切 5 帧 ─────────────────────► 0x110 ~ 0x114
```

为此在 `uart_link` 里抽出四个复用入口（声明见 `uart_link.h`）：

| 函数 | 作用 |
|---|---|
| `ulink_apply_cmd12(const uint8_t *f)` | 施加一帧 12B 命令（帧头 + CRC 校验 + 命令落地） |
| `ulink_build_fb_frame(uint8_t *out, uint32_t now)` | **只组** 40B 反馈，不发送 |
| `ulink_tick_watchdog(uint32_t now)` | 看门狗（两条链路共用同一套超时状态，重复调用无害） |
| `ulink_set_extra_status(uint16_t bits)` | 传输层向 `status` 注入额外位（供 `CAN_ERR` 用） |

**好处**：命令落地、CRC、看门狗、30+ 个字段语义**全世界只有一份实现**，
串口与 CAN 行为天然一致，不会出现「串口能跑、CAN 有偏差」的分裂。

#### 帧映射细节

| CAN 帧 | DLC | 映射规则 |
|---|---|---|
| `0x000` | **任意（含 0）** | 拼 12B 帧 `cmd = ULINK_CMD_ESTOP` → 急停（退小陀螺→停车→断 STBY→锁存） |
| `0x020` | **必须 8** | `[cmd, seq, vx(2), vy(2), wz(2)]` → 12B 帧的第 4~9 字节 |
| `0x021` | ≥ 1 | 只更新 `s_flags`，**不产生命令帧**（见下） |

`0x020` 若 DLC < 8 直接丢弃并计入 `rx_short`（速度命令必须满 8 字节）。

#### 编译开关与互斥保护

```c
/* can_link_config.h —— 联调期 1，整定期 0 */
#define CAN_LINK_ENABLE  1

/* can_test_config.h —— 排障期 1，平时 0 */
#define CANTEST_ENABLE   0
```

两者**编译期互斥**：

```c
/* can_link.c 顶部 */
#if CAN_LINK_ENABLE && CANTEST_ENABLE
#error "can_link 与 can_test 不能同时启用：两者都要初始化 CAN1，会互相打架"
#endif
```

`main.c` 全部用 `#if` 包住各自的 `init/poll`，**不再靠注释代码切换**，也不怕 CubeMX 重新生成。

#### 发送策略：TX 队列连续发（对应 §3.4 风险②）

F407 只有 **3 个发送邮箱**，一组 5 帧塞不进去，所以：

- 维护 **20 帧深**的 TX 环形队列（`CANLINK_TX_QUEUE_SIZE`）
- 主循环每轮 pump 一次：`while (队列非空 && 发送邮箱有空) AddTxMessage()`
- **只有 `AddTxMessage` 成功才推进 tail**，失败原样留着 —— **不丢帧**
- 反馈**整组进队列，或整组丢弃**，绝不发残缺组（避免接收端拼出半帧）

#### 两个容易踩的语义细节

**① `0x021` 是标志帧，不是命令帧**

`flags` 的 `EN`（bit0）被清成 0 时 F407 **立即停车**，但：

- **不**走 `ulink_apply_cmd12()` —— 否则反馈里的 `cmd_cnt` 会莫名 +1，破坏上位机的丢包率统计
- 直接调 `chassis_stop()`，并**故意不刷新** `s_ctrl_seen`（EN=0 不是控制帧，看门狗应照常计时）

**② `cmd_cnt` 的统计口径**

只统计 **`0x020` 与 `0x000`**；`0x021`（无论 EN 是 0 还是 1）**都不计入**。
上位机算丢包时，按「自己发出的 `0x020` 帧数」比对即可。

#### `CAN_ERR` 阈值

读 `CAN_ESR` 的 TEC / REC，**任一 > 96** 即置位（96 是 error-passive 的预警线，127 才真正降级）。
**是实时状态位，不是锁存位**：计数降回来自动清零。

#### 使用方式

```c
/* main.c —— USER CODE BEGIN 2，必须在 MX_CAN1_Init() 之后 */
#if CAN_LINK_ENABLE
  can_link_init();
#endif

/* main.c —— while (1) 里 */
#if CAN_LINK_ENABLE
  can_link_poll();     /* 收命令 + 看门狗 + 100 Hz 反馈 + TX pump */
#endif
```

联调期把 `CAN_LINK_ENABLE` 改 `1` 编译烧录；整定期改回 `0`。

验证命令（对应 §9 联调顺序）：

```bash
candump -td can0          # 应看到 0x110~0x114 每 10ms 一组、组内连续
cansend can0 021#00       # EN 关 → 停车（注意 cmd_cnt 不变）
cansend can0 000#         # 广播急停（DLC=0 也认）
cansend can0 021#01       # EN 开 → 允许驱动，之后速度才生效
candump can0 | grep 113   # 从 0x113 看 status 位翻转与 cmd_cnt
```

## 9. 联调步骤（建议顺序）

1. F407：`CANTEST_ENABLE=1` 烧录 → `candump can0` 看到 `0x7F0` 心跳（500 ms）
2. 双向：`cansend can0 200#01` → 收到 `0x201` 应答（**已实测 ✅**）
3. Jetson：`CanChassisLink` 上线 → `candump` 看到 `0x020`/`0x021` 与 `0x110~0x114`
4. 组规则：故意丢帧/插帧 → 确认拼帧输出不跳变、坏组被丢弃
5. ZDT：切 CAN 模式（1 Mbps）→ `candump` 看到扩展帧应答
6. 速度命令 **50 mm/s 起步**，逐步加

### 9.1 2026-10-21 本机实测（Jetson CANable 2.0 ↔ F407）

F407 烧录 `CAN_LINK_ENABLE=1` 固件后，Jetson 以 `--device can0` 运行上位机：

| 项 | 结果 |
|---|---|
| 发 | `0x020` 速度命令 + `0x021` flags 正常上总线（candump 可见） |
| 收 | `0x110~0x114` 拼回 40B，`valid=1`；组间隔 ~9.2ms（≈100Hz）、组内延迟 ~100µs（远小于 2ms 承诺） |
| status | `0x00D3`：IMU 在线+标定+驱动使能+**LINK_OK**（收到命令、看门狗位清零） |
| 组规则 | 自检 `[8]` 全绿（顺序/乱序/缺帧/CRC 坏组/非反馈帧） |
| 云台 ZDT | 扩展帧在发（`0x000100/0x000200 35/36 6B` = 遥测轮询），**电机仍 UART 模式 → 无应答**（待切 CAN 模式 + 1M） |
| UDP 链路 | 客户端 `--selftest --host 192.168.2.2` 收到遥测回包，无坏包 |

联调中修掉的两个 Jetson 侧问题：
1. `CanTransport` 的 socket 没设非阻塞 → `gimbal.step()` 里一读就阻塞，主循环卡死（只发出第一帧就停）。已加 `O_NONBLOCK`。
2. `0x020` 在 100Hz 循环下用严格 `>= 10ms` 判断，因浮点/调度抖动隔一拍才发（~20ms/帧）→ 加 0.9x 容差，恢复 ~10ms/帧。

F407 侧：`UserLib/Comm/can_link_config.h` 的 `CAN_LINK_ENABLE` 需为 **1**（联调期），整定期改回 0。

### 9.2 2026-10-21 本机实测第二轮（全 CAN 准备）

- CANable 2.0 换了一台机器后 `/dev/ttyACM*` 编号变为 **`ttyACM1`**：
  `sudo slcand -o -s8 -t hw /dev/ttyACM1 can0 && sudo ip link set can0 up` → `can0` 状态 **UP**（`ip -br link show can0` 有 `<NOARP,UP,LOWER_UP>`）。
- CH340（`/dev/ttyUSB0`）当时未插，混合模式（`--chassis can0` + 云台 UART）无法启动，日志报
  `[main] 打开 /dev/ttyUSB0 失败：No such file or directory`。
- **据此定案（2026-10-21，v0.4）：全部改 CAN** —— 云台 ZDT 也走同一根 `can0`（1 Mbps、面板/上位机切 CAN 模式），
  上位机改为 `--device can0` 全 CAN 运行，CH340 彻底退役（仅保留作为备份/调试）。
- 好处：少一根 USB 串口、少一层 CH340 总线争抢（F407 反馈 + ZDT 应答抢线问题不复存在）、
  带宽余量充足（§3.3 估算合计约 10%，其中总线只有这一条）。
- 切换顺序（建议）：①ZDT 面板/上位机 → CAN 模式 + 1 Mbps；②`candump can0` 确认 ZDT 扩展帧应答；
  ③Jetson 上位机 `--device can0`；④先 `g`/`f` 使能，速度 50 mm/s 起步。

### 9.3 2026-10-21 第三轮：接线修复后全链路实测通过

**测试条件**：F407 `CAN_LINK_ENABLE=1`；`slcand -o -s8 -t hw`（1 Mbps）；`can0` UP。

#### ① F407 → Jetson 反馈（100 Hz）

```
抓 2 秒：997 帧
  0x110 × 200   0x111 × 200   0x112 × 199   0x113 × 199   0x114 × 199
完整组 199/200，CRC 通过 199/199
组内延迟 0.06 ~ 0.13 ms，组间隔 ≈ 9.97 ms
```

单组字节（示例）：

```
110  [8]  5A A5 81 00 00 00 00 00    帧头 + 类型 0x81 + seq + x[0..3]
111  [8]  00 00 00 00 B2 FF 00 00
112  [8]  00 00 00 00 66 00 00 00
113  [8]  51 00 00 00 BE 3B 00 00
114  [8]  00 00 00 00 00 00 5A 0D    帧尾 0x0D
```

解码（静止状态）：

| 字段 | 值 |
|---|---|
| `status` | `0x0051` = `IMU_ONLINE` + `DRIVER_ON` + `GYRO_ON` |
| `cmd_cnt` | 0（尚未收到命令） |
| 里程计 | x=0 mm，y=0 mm，yaw = -0.78° |
| 正解速度 | vx=0 mm/s，vy=0，wz=0.00 rad/s |
| 四轮 RPM | `[0, 0, 0, 0]` |

#### ② Jetson → F407 命令（双向确认）

发送 `0x021#00`（flags=0）+ 3 帧 `0x020#0100000000000000`（零速度）：

| 观察项 | 结果 |
|---|---|
| `cmd_cnt` | **0 → 3**，与发出的 3 帧 `0x020` 精确对应 |
| `LINK_OK`（0x0002） | 点亮（收到命令后看门狗位清零） |
| `0x021` 是否计入 `cmd_cnt` | **不计入** ✅（与 §8.1 约定一致） |
| `status` | `0x0055` = `IMU` + `LINK_OK` + `WDOG` + `DRV_ON` + `GYRO` |

> `WDOG` 点亮是因为发完 3 帧后停手超过 100 ms，符合预期。

#### ③ 云台 ZDT（同一根总线，1 Mbps）

| 地址 | 结果 |
|---|---|
| **addr 1（yaw）** | ✅ **正常应答** |
| addr 2 ~ 16 | ❌ 无应答（总线上只能看到自己发出的请求帧） |

yaw 三个读取命令回包：

```
GetVbus   0x24  →  24 2F D6 6B     母线电压 = 54.83 V
GetStatus 0x3A  →  3A 03 6B        状态 = 0x03
GetEnc    0x31  →  31 A7 84 6B     编码器 = 33959
```

**结论**：`0x110~0x114`（11-bit 标准帧）与 ZDT（29-bit 扩展帧）在同一根 1 Mbps 总线上混跑
**互不干扰**，§1/§3 的隔离设计得到实测验证。

**总线当前节点数**：F407 + CANable 2.0 + ZDT yaw = **3 个**。
（pitch 尚未接入，所以断电量 `CAN_H ↔ CAN_L` 约 **60 Ω**，4 节点全接入时应为 **~40 Ω**。）
